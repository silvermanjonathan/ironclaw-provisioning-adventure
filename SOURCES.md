# Sources — where each "right answer" comes from

Every safe choice in this book corresponds to a practice an engineer building on IronClaw would find in the documentation. This file maps each decision page to its source. Column three is honest about the difference between **documented** (the docs say this) and **adapted** (the docs establish the principle or mechanism; the book dramatizes it).

| Page | Safe choice(s) | Status | IronClaw documentation basis |
|---|---|---|---|
| 2 | System keyring | **Documented** | Onboarding wizard, step 2: "System keyring is recommended; use an environment variable on servers/containers without a keyring." The env-var option in the book is the docs' own sanctioned fallback — which is why it tempts. (`docs.ironclaw.com/onboard`) |
| 6 | Sandbox on | **Documented** | Wizard step 7, Docker sandboxing: LLM-originated commands run "with no access to credentials, limited filesystem reach, and network restricted to an allowlist. Can be disabled in environments without Docker." On is the shipped posture; the book's pressure is the documented off-switch. (`docs.ironclaw.com/onboard`, `/security`) |
| 9 | Poll out / one locked tunnel | **Documented** | A tunnel exists for webhook channels "and for instant message delivery when you don't want polling" — polling is the documented no-inbound alternative. The web gateway defaults to `127.0.0.1` ("local-only… recommended"); exposing it directly is "generally not recommended"; public endpoints require channel-level auth and least-privilege. (`docs.ironclaw.com/tunnel`, `/channels/local`, infrastructure guides) |
| 13 | Look-only, or a person presses the button | **Adapted** | The docs' least-privilege principle applied to the processor-side credential. IronClaw scopes where a secret may be sent (`host_patterns`; credentials injected at the proxy, never visible to tools) and its security notes require "least-privilege access" on exposed endpoints — but read-only / prepare-with-approval / unattended tiers are issued by the payment processor, not toggled in IronClaw. Correct builder practice; not a product switch. (`docs.ironclaw.com/security`) |
| 18 | Trim the list to two websites | **Documented** | Tools declare `network.allowed_hosts`; anything else is "rejected by the proxy before the TCP connection is established." "Review `capabilities.json` before installing any WASM tool from an untrusted source." Trimming the list is that review. (`docs.ironclaw.com/security`, `/capabilities/sandboxed-tools`) |
| 22 | One case at a time | **Adapted** | `workspace.allowed_prefixes` "scopes which memory paths a component may touch" — the documented mechanism. The per-dispute assemble-then-clear workflow built on it is invented practice. (`docs.ironclaw.com/security`, `/capabilities/memory/memory`) |
| 55 | Paired phones, or a short allowlist | **Documented** | The Telegram channel config documents `dm_policy` — `open` / `allowlist` / `pairing` — with `pairing` as the shipped default: "the bot DMs back a pairing command that must be run in the terminal." `allow_from` and `owner_id` are the documented allowlist forms. Open is a documented position of the same switch. (`docs.ironclaw.com/channels/telegram`) |
| 28 | Read the code first; or reduced powers | **Documented** | Nearly verbatim: "A skill in a trusted directory has the same tool access you do. Never place a skill file there without reading it first." ClawHub-installed skills run attenuated — "read-only tools only — no shell, no file write, no HTTP." The book's broken demo reproduces the documented fail-closed behavior of a reduced-trust install. (`docs.ironclaw.com/capabilities/skills`) |
| 32 | Set all three limits | **Adapted** | The guardrails block is documented — `rate_limit`, `max_tool_calls`, `max_tokens`, `timeout_secs` — including the imperative "Always set `rate_limit` on webhook-triggered routines." The currency-denominated spend cap is invented: IronClaw caps tokens, calls, and runs, not dollars. It is the ceiling this domain needs, which is part of the lesson — but do not expect a dollar field. (`docs.ironclaw.com/capabilities/routines/reactive`) |
| 37 | Tune the channel | **Adapted** | Logging, the safety layer, and real-time leak detection are documented; the severity-filter tuning evening dramatizes that class of work rather than naming a feature. (`docs.ironclaw.com/security`) |
| 59 | Apply the waiting update | **Documented** | "Keep current with `ironclaw-update`" is the docs' own imperative, stated without exceptions. The launch-eve deferral pressure is the dramatization. (`docs.ironclaw.com/quickstart`) |

Two further groundings worth knowing:

- **The "two manuals disagree" device (pages 9 and 32) is itself sourced.** The compiled IronClaw docs list real self-contradictions — MCP transport support and the skill token-budget default — and the book's contradictions are modeled on that documented pattern, not invented from nothing.
- **The ending citations are real and external.** EchoLeak (CVE-2025-32711), CVE-2025-6514, the Nx "s1ngularity" worm, the ~1.5M-token exposure, the ~135,000-instance scan, the runaway-loop cost case, and the patched-before-disclosure RCE (CVE-2026-25253, fixed in build 2026.1.29) are all public record. The EchoLeak citation appears on more than one ending, each time for a different facet of the same documented incident. What remains fiction is every event at Quillon: no IronClaw incident, save, or failure is depicted, because none is on the public record.

Docs drift. These references were compiled 2026-07-25 against `docs.ironclaw.com`; verify wording against the live pages before relying on it — which is, after all, the book's entire thesis.
